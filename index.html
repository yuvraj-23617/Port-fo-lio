From paper to shipped.

/ FOUR MOVES I KEEP COMING BACK TO — SHAPED BY REPRODUCING LIGHTGCN FROM SCRATCH.

/ 01

Model

Read the paper before you type. When reproducing LightGCN, the first job wasn't writing PyTorch — it was understanding what the original GCN was doing wrong, and why a simpler propagation could outperform it. The data has a shape; the model should follow it, not impose one.

/ 02

Build

From scratch means from scratch. Adjacency normalisation, layer-wise propagation, the ranking objective — each piece built and verified in isolation before it composed with the next. The paper's own ablations were a warning: more layers is not more signal.

/ 03

Test

Match the protocol, not just the metric. We ran the same leave-one-out split and negative sampling the paper used, so any deviation we saw was a property of the model — not of our testing. Ablations over depth and dimension were as much about understanding our own implementation as measuring it.

/ 04

Ship

A result is only as trustworthy as the caveats attached to it. Write down what you can't claim — the small sample, the incomparable baseline, the variance you haven't ruled out. Shipping means being honest about scope, not just loud about the number.

/ CODEJUDGE — DISTRIBUTED CODING ASSESSMENT PLATFORM · SPRING BOOT · RABBITMQ · DOCKER

Running untrusted code at scale.

3LANG

ROLE — DESIGN + FULL-STACK IMPLEMENTATION
STACK — SPRING BOOT · RABBITMQ · DOCKER · POSTGRESQL · MONACO
RESULT — ASYNC JUDGE FOR PYTHON, JAVA & C++
DEPLOY — ONE-CLICK DOCKER COMPOSE, 12 PRE-LOADED PROBLEMS

01 / PROBLEM

Synchronous judging doesn't scale.

Traditional coding platforms run submissions inline — the request thread blocks while the compiler runs and test cases execute. Under any real load that means queue buildup, timeouts, and broken UX. And the moment you're executing code someone else wrote, you're already in security territory.

02 / APPROACH

Decouple submission from execution.

The submission endpoint only validates and enqueues: the submission is saved in PostgreSQL with verdict PENDING, and its ID is published to a RabbitMQ queue. A judge worker consumes the message, writes the code to a temporary directory, executes it inside an isolated Docker container, compares the output against visible and hidden test cases, and writes the final verdict back. The frontend polls the submission until the verdict lands — Spring Boot handles the API, PostgreSQL holds users, problems, submissions and test cases.

03 / DECISION

Sandbox everything, trust nothing.

Every submission runs in a fresh container with networking disabled and hard resource caps: 128MB memory and 0.5 CPU for Python, 512MB and 1.5 CPU for Java and C++, with an execution timeout on top. It costs latency, but you cannot run arbitrary user code on the same machine that holds your database. This was the design decision I'd defend hardest in review — the trade-off is deliberate.

04 / OUTCOME

Async, multi-language, and instructor-friendly.

Three languages supported (Python, Java, C++), submissions judged asynchronously with verdicts of ACCEPTED, WRONG_ANSWER or RUNTIME_ERROR plus recorded execution time. 12 pre-loaded problems ship with visible and hidden test cases, role-based access separates admins from users, and the admin dashboard lets instructors create, edit and delete problems and test cases without touching the codebase. The candidate UI is a real terminal — because the assessment should feel like the tools engineers actually use.

05 / NEXT

What I'd carry forward.

Replace polling with WebSocket live verdicts and move to JWT stateless auth. Persist submission history in the database instead of local storage, add Redis caching for problems and test cases, and scale out with multiple judge workers under Kubernetes with a CI/CD pipeline. And harden the sandbox further — the security model is never done.

"The hard part isn't running code — it's running untrusted code safely."

/ E-SUMMIT'26 — IIIT-DELHI'S FLAGSHIP ENTREPRENEURSHIP SUMMIT

Qualify the prospect, then pitch.

0×

ROLE — HEAD OF SPONSORSHIP DOMAIN
WINDOW — OCT 2025 → MAR 2026
RESULT — 5× GROWTH IN THE SPONSORSHIP VERTICAL

01 / PROBLEM

Prospect conversion was the broken step.

On paper the workflow was straightforward: identify prospects, assign them to team members, make calls, send emails, follow up, close the sponsorship, and hand the agreed deliverables to the event teams. We tracked prospects and follow-ups in Google Sheets and reviewed progress in weekly meetings. But conversion stayed flat — we were sending everyone the same generic pitch: "we are organising an entrepreneurship summit; would you like to sponsor us?" Team members could make the calls and send the emails quickly, but the company had little reason to respond. We were optimising for the number of companies contacted rather than whether the company had a specific reason to participate.

02 / THE FIX

Research before outreach.

I changed the workflow so that prospect research became part of the process, before anyone reached out. Instead of one pitch for everyone, we identified something specific about each company that could connect to our student audience. Approaching a major consumer brand, we tied a seasonal campaign it was already running to our student audience and positioned E-Summit as a campus opportunity to activate that campaign. We used similar company-specific approaches for other prospects. At the same time we split specialised outreach across the team — some members handled banks and PSUs through offline outreach, while others focused on gaming partnerships.

03 / SECOND FAILURE

The workflow broke again after the close.

A second problem appeared once sponsors signed on. On event day the workflow became error-prone: each sponsor could have multiple commitments — branding, activations, placements and other agreed benefits — and missing one could delay or affect the final payment. Fulfilment required coordination across different event teams, so the sponsorship vertical had to track what had been promised and whether each item had actually been delivered.

04 / CONSTRAINT

March is the wrong month.

There was also a constraint we could not fully work around: E-Summit happens in March, close to the end of the financial year. Some companies were already closing their budgets and sponsorship decisions, which meant that even interested companies sometimes could not complete the process within our timeline. We couldn't remove the constraint — but knowing it let us prioritise the prospects who could still move in time.

05 / OUTCOME

Same team, different shape of work.

If I were fixing the workflow from scratch, I would fix prospect qualification and personalisation first. Increasing outreach volume would only have made the first problem larger — more generic pitches to companies with no clear reason to respond. Once we changed how we selected and approached prospects, conversion improved without simply increasing the number of calls and emails. The overall sponsorship vertical grew 5× compared with the previous edition.

"More outreach volume would only have made the first problem larger."
